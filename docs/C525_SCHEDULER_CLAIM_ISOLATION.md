## 1. Finding

The refreshed PR #24 baseline was `13c33f5ecd992dc735fdf6edff0fa4d41c74e79a`. Both scheduler paths called `runtime.claim(limit)`; the runtime used unrestricted `claim_delivery_jobs(p_limit)`, whose SQL did not filter `delivery_ledger.kind`. The Weekly application feature gate did not provide database-level isolation against a Daily claim path.

## 2. Database remediation

Migration `202611260039_delivery_kind_scoped_claims.sql` adds:

| RPC | Literal allowed kind |
|---|---|
| `public.claim_daily_delivery_jobs(integer)` | `daily_reminder` |
| `public.claim_weekly_delivery_jobs(integer)` | `weekly_newsletter` |

Each RPC independently applies its literal kind predicate to retry-exhaustion cleanup, candidate selection before ordering/batch limiting, and the final claim UPDATE. Both preserve five-minute leases, fresh claim tokens, bounded five-attempt retry handling, expired-lease reclaim and retry-exhaustion terminalization. Database time is used for claim timestamps.

The historical unrestricted `claim_delivery_jobs(timestamptz, integer)` remains for historical migration/test provenance, but execution is revoked from `PUBLIC`, `anon`, `authenticated` and `service_role`. Only the two kind-specific RPCs are granted to `service_role`.

Both new functions use `SECURITY INVOKER`; no new `SECURITY DEFINER` function or generic kind-selecting helper is introduced. They use the existing service-role ledger privileges and RLS-bypass role.

## 3. Application and scheduler safeguards

- Scheduler derives an expected `DeliveryKind` from the exact Cron schedule and requests that kind.
- Supabase runtime selects the corresponding RPC.
- Runtime rejects any returned row whose kind differs from the request.
- Scheduler independently checks every returned job before processing.
- `DELIVERY_ENABLED=false` remains the first global stop.
- `WEEKLY_DELIVERY_ENABLED === "true"` remains a separate opt-in, checked before Supabase runtime construction.
- Existing current-consent authorization, recipient resolution, stale-token validation, claim expiry, provider idempotency and transport authorization remain in the pipeline.
